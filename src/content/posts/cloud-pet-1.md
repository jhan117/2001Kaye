전에 학교 과제로 만들었던 토이 프로젝트를 Railway에 배포해 둔 적이 있다. 하지만 무료 트라이얼 기간이 만료되면서 백엔드와 DB가 모두 정지된 채 방치되어 있었다.

이번 기회에 아키텍처를 전체적으로 다시 점검하고, 지속 가능한 무료 플랫폼인 **Render(백엔드)와 Supabase(DB)로** 이전하기로 했다. 더불어 Render 무료 플랜 특성상 한동안 요청이 없으면 서버가 Sleep 모드로 들어가 대기 시간이 발생하는 문제도 함께 해결해 보기로 했다.

## 기존 vs 변경된 기술 및 배포 환경

### 기존 환경

- **Frontend**: React -> Netlify
- **Backend**: Spring Boot (Java) -> Railway _(Trial 만료)_
- **Database**: MySQL -> Railway _(Trial 만료)_

### 변경된 환경

- **Frontend**: React -> Netlify _(유지)_
- **Backend**: Spring Boot (Java) -> Render + **UptimeRobot** _(서버 sleep 방지)_
- **Database**: **PostgreSQL** -> **Supabase** _(MySQL 무료 배포 환경의 한계로 전환)_

## 주요 작업 및 트러블슈팅

### 1. Supabase 데이터베이스 구축

무료 티어 지원이 훌륭하고 안정적인 Supabase를 도입했다.

- 서울/도쿄 리전으로 프로젝트 생성 (환경변수로 접근할 DB 접속 비밀번호 안전하게 저장)
- 권한 에러(RLS 관련) 방지를 위해 기본 보안 설정 유지하며 인스턴스 생성

### 2. 백엔드 코드 및 설정 마이그레이션

#### `build.gradle` 및 자바 버전 정돈

- **Java 버전 변경**: 안정적인 LTS 버전 조정을 위해 Java 24에서 **Java 21 LTS**로 세팅 (`JavaLanguageVersion.of(21)`)
- **의존성 교체**: `com.mysql:mysql-connector-j` 제거 -> `org.postgresql:postgresql` 추가
- **패키지 리팩토링**: 기존 학번/전적대 기반 패키지명을 표준 프로젝트 패키지명(`com.cloudpet.cloudpetbackend`)으로 일괄 리팩토링 (`group = 'com.cloudpet'`)

#### `schema.sql` PostgreSQL DDL 변환

- MySQL 전용 구문(`USE`, `DROP/CREATE DATABASE`) 제거
- `AUTO*INCREMENT` -> `GENERATED BY DEFAULT AS IDENTITY` 로 변환 (수동 데이터 삽입 유연성 확보)
- 멱등성 배포를 위해 모든 테이블 생성문에 `IF NOT EXISTS` 구문 추가

#### 프로필 분리 (`application.properties`)

- DB 드라이버를 `org.postgresql.Driver` 로 변경
- 로컬 환경(`application-local.properties`)과 배포 환경(`application-prod.properties`) 분리
  - 로컬: 테스트 데이터 자동 주입(`data-dev.sql`) 및 Supabase direct 연결
  - IntelliJ 실행 구성(Run/Debug Configurations)의 `Active profiles`에 `local` 지정
  - 내 컴퓨터 RAM 절약 및 로컬 DB 프로그램 설치 없이 클라우드 DB 직접 바라보도록 설정

#### 전역 CORS 설정 리팩토링

- 각 컨트롤러에 파편화되어 있던 `@CrossOrigin` 어노테이션 전면 제거
- `WebMvcConfigurer`를 구현한 `WebConfig.java`를 작성하여 프론트엔드 도메인(Netlify) 대상 전역 CORS 룰을 깔끔하게 일관화

### 3. 백엔드 배포 (Render) & 트러블슈팅

Docker 멀티 스테이지 빌드 기반으로 Render Web Service를 구성했으나 몇 가지 예외 상황에 직면했다.

#### Issue 1. Dockerfile 베이스 이미지 이슈

- 기존 Dockerfile의 Java 이미지명이 빌드 서버에서 마운트되지 않음
- Java 21 LTS 공식 경량 이미지인 `eclipse-temurin:21-jdk` 로 1, 2단계 멀티 스테이지 베이스 이미지 교체

#### Issue 2. Render(IPv4) ↔ Supabase Direct(IPv6) 네트워크 불일치 (`Network is unreachable`)

- **현상**: 로컬 환경에선 잘 붙던 DB 커넥션이 Render 서버에만 올라가면 네트워크 거부 발생
- **원인**: Supabase의 Direct Connection 주소는 **IPv6 전용**인 반면 Render 무료 서버 환경은 **IPv4 전용** 네트워크로 구동됨. (로컬 내 컴퓨터는 IPv4/IPv6 듀얼 스택이라 접속이 가능했던 것)
- **해결**: Supabase에서 제공하는 **IPv4 지원 Session Pooler** 주소로 접속 엔드포인트 변경
  - Connect -> Direct -> Connection Method에서 확인 가능

#### Issue 3. Hibernate Dialect 자동 감지 실패 (`Unable to determine Dialect without JDBC metadata`)

- **현상**: 런타임 시 Hibernate가 DB metadata 핑으로 Dialect을 자동 감지하다가 커넥션 초기화 실패
- **해결**: `application-prod.properties`에 PostgreSQL Dialect을 명시적으로 고정 지시

```properties
spring.jpa.database-platform=org.hibernate.dialect.PostgreSQLDialect
```

### 4. 서버 Sleep 방지 핑 구조 설계 (UptimeRobot)

Render 무료 플랜의 15분 미사용 Sleep 모드를 방지하기 위해 UptimeRobot을 도입했다.
기존 비즈니스 로직 API(`/api/care-plans`)로 핑을 쏘면 DB 조회가 매번 발생하므로 별도의 전용 헬스체크 컨트롤러를 구축했다.

```java
@RestController
@RequestMapping("/api/health")
public class HealthController {

    @GetMapping
    public String healthCheck() {
        return "OK";
    }
}
```

- **장점**: DB 부하 0%, 0.001초 미만의 즉각적인 `200 OK` 응답 반환
- UptimeRobot에 5분 주기 `GET https://cloudpet-backend.onrender.com/api/health` 핑 등록 -> **24시간 슬립 없는 백엔드 완성**
- 근데 주소를 `/api/` 없이 `/health` 이렇게 쓰는 것이 더 국룰이라고 한다.

## 마무리

기존의 단순 배포에서 그치지 않고 데이터베이스 마이그레이션부터 듀얼 스택 네트워크 매핑(IPv4/IPv6), 전역 CORS 리팩토링, healthcheck 기반 핑퐁 세팅까지 배포 전반의 품질을 올릴 수 있었던 경험이었다.
